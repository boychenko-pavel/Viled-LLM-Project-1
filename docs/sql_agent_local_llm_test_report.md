# Отчёт о тестировании SQL-агента в локальном режиме

Дата: 3 августа 2026 года.

## Итог

- Бизнес-матрица: **100/100** тестов пройдено, из них 50 средней и 50 высокой сложности.
- Все вопросы уникальны: 100 идентификаторов и 100 формулировок.
- Все 6 примеров из веб-интерфейса формируют SQL с ожидаемым доменом, фильтрами, агрегациями и лимитами.
- Полный regression-набор проекта: **398 passed, 226 subtests passed**.
- `python -m compileall -q sql_agent langchain_sql_agent.py`: успешно.
- LM Studio доступен на `http://127.0.0.1:1234/v1`, настроенная модель `llama-3.2-3b-instruct` загружена; прямой smoke-тест вернул `LOCAL_OK`.

## Методика

Локальный SQL-режим проверялся в штатной архитектуре: сначала детерминированный `IntentParser`, затем `SqlBuilder`; локальная модель используется только как fallback для неизвестного намерения. В матрице вызов LLM намеренно запрещён: это подтверждает, что документированные бизнес-вопросы не зависят от вероятностного ответа модели. Отдельный прямой вызов подтвердил работоспособность локальной модели.

Для каждого SQL-кейса проверялись:

- операция и бизнес-домен;
- таблицы, колонки, связи и ключи соединений;
- даты, валюты, идентификаторы и dimension-фильтры;
- агрегаты, `GROUP BY`, `HAVING`, сортировка и `TOP`;
- отсутствие запрещённых или недокументированных полей;
- read-only валидность итогового SQL.

Состав 100 тестов:

| Набор | Средние | Сложные | Всего |
|---|---:|---:|---:|
| Формирование SQL | 42 | 48 | 90 |
| Уточняющие ответы | 4 | 1 | 5 |
| Допустимый явный `SELECT` | 2 | 1 | 3 |
| Блокировка опасного SQL | 2 | 0 | 2 |

Покрытие SQL-кейсов: sales — 22, retail price — 19, purchases — 13, stock — 13, product cost — 11, product dimension — 11, division dimension — 1.

До исправлений второй пример ошибочно маршрутизировался в продажи. Остальные пять примеров выбирали правильный домен, но часть общих SQL-механизмов требовала корректировки.

## Исправленные ошибки

1. Исправлена маршрутизация «карточка/карточку товара» в `dimension_product`.
2. Устранён жадный захват составных фильтров: brand, BU, category и season теперь разделяются корректно, включая русские падежи.
3. «Выручка» и «оборот» без слова «сумма» распознаются как `SUM` соответствующей валютной колонки.
4. Исправлены естественные рейтинги по товарам, брендам, городам, подразделениям, складам и типам операций.
5. Добавлены нативные фильтры sales по `document_number`, `channel`, `payment_method`, `partner_id`, `customer_status` и `division_id`.
6. «Все проданные товары» теперь строится как группировка по `product_id` с `HAVING SUM(quantity) > 0`, без повторяющихся детальных строк.
7. Исправлена семантика дат: диапазоны нормализуются, datetime-конец периода включается через следующий день, «после даты» начинается со следующего календарного дня.
8. Для stock-порогов используется `HAVING` по суммарному остатку; отрицательные движения не отбрасываются до агрегации.
9. Закупочная стоимость за единицу рассчитывается через `NULLIF(quantity, 0)`; групповой расчёт использует взвешенную формулу `SUM(amount) / SUM(quantity)`.
10. GM приведён к документации: НДС 16%, последняя эффективная цена, актуальный cost balance, скидка и стабильный порядок обязательных колонок.
11. Итоги sales считаются по всему отфильтрованному набору до применения `TOP`, а не только по отображаемым строкам.
12. Детальные ответы ограничены `TOP 100`, preview — `TOP 10`; запросы «все строки/без лимита» требуют пагинацию или экспорт.
13. Закрыт обход ограничения явного SQL через оконный/вложенный агрегат, CTE, `UNION`, `TOP > 100`, `PERCENT`, `WITH TIES` и незавершённый `OFFSET`.
14. Явный безопасный `SELECT` выполняется как написан и не блокируется семантическими уточнениями обычного языка.
15. Ответ локального LLM теперь проходит whitelist-проверку домена, таблицы, колонок, метрик, фильтров, дат, сортировки и лимита.
16. `COUNT(DISTINCT document_number)` отделён от подсчёта строк; для grouped `COUNT(*)` добавлен полный итог до `TOP`.
17. Добавлены plural-разрезы по category, article, season, size, collection и BU для всех документированных fact-доменов.
18. Явный контекст `[DWH].[LLM].[stock]` и «движения склада» имеет приоритет над совпадающими названиями purchase-операций.
19. Пороговые условия поддерживают `>=`, `<=`, отрицательные значения и десятичную запятую; фильтр применяется через `HAVING` или после расчёта GM.
20. Детальные продажи в USD/EUR сохраняют `amount_usd`/`amount_eur` и соответствующий `ИТОГО`; недокументированные `price_usd`/`price_eur` больше не генерируются.
21. «Последние N» цен или cost-операций возвращает N строк истории, а не ошибочно одну строку `rn = 1`.
22. Read-only validator теперь блокирует `SELECT INTO`, `NEXT VALUE FOR`, второй оператор после комментария/перевода строки и сериализацию безлимитного вложенного результата.
23. Категориальные вопросы «сколько брендов/артикулов/категорий/каналов» формируют `COUNT(DISTINCT ...)`; разрез и полный distinct-итог не теряются.
24. Текущая средняя себестоимость рассчитывается по последнему balance как `cost_sum / qnt_sum`; добавлен явный выбор обычного и взвешенного среднего по операциям.
25. Исправлены строгие/включительные границы дат, точные даты вида `15 марта 2026` и отклонение обратных диапазонов.
26. Исправлены синонимы числовых порогов; двусторонний диапазон больше не применяется частично.
27. Запросы к нескольким fact-доменам вне GM и конфликты явной таблицы со смыслом требуют уточнения, а не дают частичный SQL.
28. GM top/min/max сортируется по `gross_margin_percent`; некорректная скидка не игнорируется.
29. Составные dimension-фильтры сохраняют валюту, дату, город, тип операции и второй атрибут; списки через `и/and`, апострофы и скобки обрабатываются безопасно.
30. Fallback локальной модели не может суммировать категориальные поля или running balances и автоматически добавляет нужный dimension join для metric/sort.
31. Read-only контур дополнительно блокирует `OPENQUERY`, `OPENROWSET`, `OPENDATASOURCE`, а материализация результата ограничена 512 KiB на ячейку и оценочными 5 MiB на ответ.

## Ограничения проверки

Проверялись формирование и семантика SQL. Запросы не отправлялись в рабочий SQL Server: тестовый запуск не читает приватный файл с учётными данными и подменяет только этап получения строк. Поэтому фактические данные, права, планы выполнения и время ответа SQL Server в этот отчёт не входят.

Правило текущей себестоимости подтверждено: последняя запись определяется по
`product_id`; `cost.db` не входит в ключ ранжирования. Реализация и regression-тест
уже используют `ROW_NUMBER() OVER (PARTITION BY product_id ORDER BY date DESC)`.
